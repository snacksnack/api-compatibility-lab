What each verdict means:

- **BLOCKED** — the sequence stops; the customer sees an error
- **CORRUPTED** — the sequence finishes and is silently wrong

## How a consequence is derived

Nothing in `workflows/` names a break. A declaration says which fields the client reads and what it does with each value; the consequence is the cell those two facts pick out of one table.

| Effect on the value | request_input | decision | record | display |
|---|---|---|---|---|
| loss | blocked | corrupted | corrupted | degraded |
| change | corrupted | corrupted | corrupted | degraded |
| novel | corrupted | corrupted | degraded | degraded |
| addition | tolerated | tolerated | degraded | tolerated |

- **loss** — the value the client read is gone or unusable
- **change** — the value is still there and is different
- **novel** — the client is handed something it has never seen
- **addition** — new material arrives alongside what was read

- **request_input** — the value is sent in a later call in the same workflow
- **decision** — the value is branched or computed on
- **record** — the value is stored by the client
- **display** — the value is shown to a person

Two rules override the table and always block: `step-missing` and `status-class-changed`. When the call itself stops working the client never reaches the field, so what it would have done with the value does not enter into it.

Which rule belongs to which effect:

| Effect | Rules |
|--------|-------|
| loss | `list-emptied`, `list-truncated`, `null-field-removed`, `populated-field-removed`, `status-class-changed`, `step-missing`, `type-changed`, `value-nulled` |
| change | `error-identity-changed`, `error-message-changed`, `order-changed`, `pagination-boundary-changed`, `status-changed`, `value-changed` |
| novel | `enum-set-grew`, `enum-value-changed`, `field-added-populated`, `value-unnulled` |
| addition | `error-shape-changed`, `field-added-empty`, `list-grew` |

Rules that can never produce an impact, because they describe the comparison rather than a value a client reads: `status-body-subsumed`, `timing-shifted`.

## Severity against consequence

Phase 3's severity is a property of the API change; the consequence is a property of this customer's integration. They are allowed to disagree, and the point of the inventory is that they do. ## Verification

Every claim above is re-derived from `replay/pairs.jsonl` by `compatlab.verify`, which does not read the rule table and asks only questions with observable answers: was this step really replayed on both sides, does the declared read really return something different on the new version, and does a blocking claim really have nothing left to send. `compatlab impact` exits non-zero while any claim is unconfirmed, so the precision figure is never computed over whichever claims happened to verify.

- **Workflow-mapping precision: 100%** (13 of 13)

What it does not verify is the judgment: whether a difference deserves to be called breaking, or whether a client's exhaustive switch really does fall through on a value it has not seen. Neither is mechanically checkable, which is why the number is named *mapping* precision. Severity has its own honesty mechanism, the hand adjudication in Phase 3.

The mapping also has to keep reaching the breaks Phase 3 caught. This is a regression guard and not evidence: the inventory is authored in this repository, so a break landing on a declared read says as much about its author as about the tool. What it catches is the mapping quietly losing one.
